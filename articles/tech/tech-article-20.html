SaaS Accessibility: A Practical WCAG 2.2 Checklist for Product Teams

Accessibility is a product-quality requirement, not a final visual polish. This guide gives SaaS product teams a practical way to review important user journeys against WCAG 2.2, combine automated checks with manual testing and track fixes through release work.

Accessibility should be part of SaaS product quality from the first design decisions, not a final visual polish. A product may work with a mouse and still be difficult to use with a keyboard, screen reader, magnification or alternative input. A repeatable review helps product teams find barriers before they become expensive to repair.

Start with the right standard and scope

Use the Web Content Accessibility Guidelines (WCAG) 2.2 as a shared reference. WCAG is organized around four principles: content should be perceivable, operable, understandable and robust. The guidelines contain testable success criteria at Levels A, AA and AAA. A product team should agree which level and which parts of the product are in scope; do not describe a product as “fully accessible” merely because a few checks passed.

Map the user journeys that matter: account creation, sign-in, password recovery, search, checkout, billing, settings, support and any workflow that is essential to the product's main purpose. Include responsive layouts and the states users encounter when forms fail, sessions expire or data is loading.

1. Make every important action keyboard-operable

  • Move through controls using Tab and Shift+Tab in a logical order.
  • Make buttons, links, menus, dialogs and custom widgets usable without a pointer.
  • Ensure keyboard focus is visible and is not hidden behind sticky headers, dialogs or floating panels.
  • Provide a reliable way to enter and leave menus, dialogs and other composite controls.
  • Do not create keyboard traps; a user must be able to move focus away from a component.

Test the complete workflow rather than checking a few isolated buttons. For example, a keyboard user should be able to open a date picker, select a date, close it and continue to the next field without losing their place.

2. Use clear structure, labels and instructions

Give each page a meaningful title and use headings in a logical hierarchy. Programmatic labels should identify form fields; placeholder text alone is not a reliable label. Group related inputs where appropriate, explain required formats before submission and identify errors in text rather than relying only on a red outline.

When a form submission fails, tell the user what needs attention and how to correct it. Associate the error message with the relevant field, preserve valid information and move focus appropriately when the user needs to act. Avoid changing context unexpectedly when someone selects a control or types a value.

3. Check contrast, resizing and touch targets

Do not communicate status through colour alone. Pair colour with text, icons or patterns. Check text and control contrast against their actual backgrounds, including hover, focus, disabled and error states. Test at narrow viewport widths and with browser zoom so that information remains available without unnecessary horizontal scrolling.

WCAG 2.2 adds criteria relevant to focus visibility, dragging movements and target size. Review controls that are difficult to activate on touch screens, especially closely spaced icon buttons and small links. A minimum target-size rule has exceptions, so apply the standard carefully rather than treating one measurement as the whole accessibility test.

4. Give images and media useful alternatives

Informative images need text alternatives that communicate their purpose or essential information. Decorative images should not create unnecessary screen-reader noise. For charts, provide the main takeaway in nearby text or a data table; a short generic label such as “chart image” is rarely enough.

Provide captions or transcripts for prerecorded media when required by the applicable accessibility criteria. Make sure controls have accessible names and can be operated with a keyboard. Do not embed important instructions only inside an image.

5. Review components and dynamic states

Modern SaaS products use menus, tabs, notifications, modals, autocomplete fields and live status updates. Make sure assistive technology can determine the name, role, value and state of each interactive control. When content changes dynamically, announce important updates without repeatedly interrupting the user with low-value messages.

Use semantic HTML elements before adding ARIA. ARIA can communicate roles and states, but it does not automatically add keyboard behaviour or correct interaction logic. A custom control still needs an accessible name, correct state, focus handling and the expected keyboard interaction.

6. Build accessibility checks into the release process

A practical review combines automated checks with manual evaluation. Automated tools can identify some missing labels, contrast issues and structural problems, but they cannot decide whether every label makes sense, whether a workflow is understandable or whether keyboard focus behaves correctly. Include manual keyboard checks and screen-reader spot checks in the test plan for important journeys.

For each issue, record the affected page or component, the user impact, evidence, severity, owner and planned fix. Re-test the corrected state and add a regression check where the same component appears throughout the product. Include accessibility acceptance criteria in design reviews and pull requests rather than leaving the whole task to a final audit.

A practical pre-release checklist

  • Every essential workflow can be completed with a keyboard.
  • Focus is visible, logical and not obscured by overlays.
  • Forms have persistent labels, useful instructions and identifiable errors.
  • Text, controls and states have sufficient contrast and do not rely on colour alone.
  • Images have appropriate text alternatives; decorative images are ignored by assistive technology.
  • Headings, landmarks and page titles describe the page structure.
  • Responsive layouts and browser zoom do not hide essential content or controls.
  • Automated results are followed by manual checks of representative user journeys.
  • Known issues have owners, severity, remediation plans and re-test evidence.

Common mistakes to avoid

Do not equate a clean automated scan with conformance. Do not add ARIA labels to compensate for unclear interface design. Do not assume a colour palette is readable because it looks attractive on one monitor. And do not make accessibility a one-time project: new features, copy changes and third-party widgets can introduce fresh barriers.

Frequently asked questions

Is WCAG 2.2 the same as a legal certification?

No. WCAG is a technical accessibility standard with testable criteria. Legal obligations depend on the jurisdiction, service, organization and applicable laws. A WCAG review is not itself a legal opinion or certificate.

Can an automated accessibility scanner test a whole SaaS product?

Automated tools can help find repeatable code-level issues, but they cannot fully assess usability, content meaning or all interaction behaviour. Combine automation with manual testing and feedback from people who use assistive technology.

Should every image have alt text?

Every image should have an appropriate text alternative decision. Informative and functional images need meaningful alternatives; purely decorative images normally use an empty alternative so they can be skipped.

When should accessibility be checked?

Include it during discovery, design, development, testing and ongoing maintenance. Check important journeys before release and re-check shared components when they change.

Key takeaway

Use this SaaS accessibility checklist to review keyboard access, focus, forms, contrast, responsive layouts, assistive technology and WCAG 2.2 testing. Treat the checklist as a starting point: adapt it to the product, organization, contractual duties and risks involved, and record decisions that need follow-up.
